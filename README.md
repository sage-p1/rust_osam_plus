## osam_plus

This library implements an Oblivious SAM+ (OSAM+) derived from [Facebook's ORAM implementation](https://github.com/facebook/oram).

⚠️ **Warning**: This implementation has not been audited. Use at your own risk!

### Minimum Supported Rust Version

Rust **1.88** or higher.

Resources
---------

- [Original Path ORAM paper](https://eprint.iacr.org/2013/280.pdf), which introduced the standard "vanilla" variant of Path ORAM on which this library is based.
- [Path ORAM retrospective paper](http://elaineshi.com/docs/pathoram-retro.pdf), containing a high-level overview of developments related to Path ORAM.
- [Oblix paper](https://people.eecs.berkeley.edu/~raluca/oblix.pdf), which describes the oblivious stash data structure this library implements. 
- [Oblivious Single Access Machines](https://eprint.iacr.org/2024/1029.pdf), which derives the SAM model from RAM, defines the behavior of an OSAM, and modifies Path ORAM to create a backend called Path OSAM.
- [Reverse-lexicographic Eviction](https://eprint.iacr.org/2013/239.pdf), referring to the deterministic order buckets in which blocks are evicted to buckets. This differs from Path ORAM, which evicts blocks to the path it reads. 
- [Oblivious Single Access Machines+](https://eprint.iacr.org/2026/451.pdf), a relaxation of the OSAM model which allows addresses to be written to multiple times. Single reads are still enforced.

Code Organization
--------------------
Within `src/`:
- `lib.rs` defines public API.
- `path_oram.rs` defines the main OSAM implementation.
- `bucket.rs` defines low-level block and bucket structs.
- `backend.rs` defines encrypted and plaintext backend structs.
- `utils.rs` contains utilities related to oblivious sorting and tree index calculations.
- `test_utils.rs` contains code shared between tests.

Overview
---------

This crate implements an oblivious SAM+ protocol (OSAM+).
OSAM+ supports three operations:

* `addr <- Alloc()` generates a fresh address that has not been allocated before.

* `Write(addr, val)` writes the given value to its associated address. Addresses can be overwritten several times. The given address must be produced by `Alloc()`.

* `val <- Read(addr)` reads and returns the value associated with the given address. Addresses can only be read once. The given address must be produced by `Alloc()`. Reading an address that was allocated but not written is a valid operation.

Design Specifications
---------------------

### Addresses

In this implementation of Path OSAM+, addresses consist of a tuple `(identifier, position)`.
An identifier is uniquely given by an increasing counter distinguish each block.
A position is a uniformly random leaf bucket a block is assigned to.

### Correctness

For correctness, the client must respect the SAM+ rules:
* Valid addresses must be generated by `Alloc()`.
* Addresses can be read at most once.
* Addresses can be written many times. Stale versions of blocks are deleted by a `Merge()` function.

There is no mechanism to enforce these rules.
It is up to the client to follow them correctly.

### Eviction

In [Facebook's Path ORAM](https://github.com/facebook/oram), the path that was downloaded in a read
or write is always the path that is evicted.
We support two eviction strategies:
* [reverse-lexicographic eviction](https://eprint.iacr.org/2013/239.pdf), which deterministically and routinely evicts buckets.
* random eviction. 

When calling a function that evicts blocks to the server, use the boolean `ordered_evict` toggle between reverse-lexicographic eviction and random eviction.

### Encryption

[Facebook's Path ORAM](https://github.com/facebook/oram) also assumes the ORAM is being run in the
secure enclave setting and does not perform encryption on-write.
We do not maintain this assumption and allow for toggling between encrypted and plaintext backends for Path OSAM+.
This can be toggled with the boolean `is_encrypted` when initializing a Path OSAM+.

### Local Operations

When calling `Write()` or `Read()`, there is one round-trip of interaction between the client and server.
In the SAM+ setting, we expect the client to be performing significantly more writes than reads.
To save on time, we introduce two functions two local functions that do not interact with the server:
* `LocalWrite(addr, val)` writes value to its associated address. Keeps the resulting block in the stash without evicting to the server.
* `LocalBatchWrite([(addr, val)])` writes a series of values to their associated addresses. Keeps the resulting block in the stash without evicting to the server.

### Evicting Multiple Paths

Traditionally, Path ORAM/Path OSAM/Path OSAM+ handle single paths at a time.
We modify Path OSAM+ to store a constant `P`, for path count.
Rather than only evicting single paths at a time, we allow `P` paths to be evicted at once.
This eliminates stale versions of blocks at a faster pace.
The stash is allowed to hold more data to handle `P` paths simultaneously.
`Read()` and `Write()` still evict one path at a time, so the function:
* `val <- ReadMultiPaths()` reads and returns the value associated with the given address while evicting `P` paths.

### Miscellaneous

There are some miscellaneous functions that:
* evict one or `P` paths to the server without reading an address.
* return the number of times a certain operation was done.
* compute the variance and standard deviation on stash occupancy (number of real blocks in the stash).
